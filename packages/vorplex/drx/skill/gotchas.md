## Declarations are children of `<x-app>`, never siblings after it

`<x-page>`, `<x-variable>`, `<x-component>`, `<x-asset>`, `<x-api>`, `<x-type>`, `<x-service>`, `<x-packages>` — every declaration node — must be a **direct child of `<x-app>`**, exactly like renderable template content (elements, `<x-route>`, `<x-page-container>`). DRX separates the two internally; the document doesn't. A `<x-page>` placed as a sibling *after* `</x-app>` closes is never discovered — the app parses with an empty page list and every `<x-page-container page="...">`/`drx.pages.<name>` reference silently fails to resolve, with no parse error to point at the mistake.

```html
<!-- Wrong: page is outside <x-app>, never found -->
<x-app>
  <x-page-container page="home"></x-page-container>
</x-app>
<x-page name="home">...</x-page>
```

```html
<!-- Right: every declaration nests inside <x-app>, alongside the shell's own template content -->
<x-app>
  <x-page-container page="home"></x-page-container>
  <x-page name="home">...</x-page>
</x-app>
```

The same rule applies one level down for a component's own nested declarations (a `<x-component>` inside another `<x-component>`, or `<x-property>`/`<x-event>`/`<x-variable>` inside a component) — they nest inside the owning `<x-component>`, not after it.

## Table layouts: the `<table>` orphan bug

DRX source is parsed with the **browser's own HTML parser**, so `<table>`/`<tbody>`/`<tr>`'s restricted content model applies to `<x-if>`/`<x-for>`/`<x-import>` exactly as it would to any other tag the parser doesn't recognize as valid table content — they get silently relocated out of the row/cell structure they were meant to wrap, *before DRX ever sees them*. This surfaces as a runtime error like `"row is not defined"`, not a parse error, so it's easy to miss in review.

```html
<!-- Breaks: <x-for> is relocated out of <tbody>, severed from the <tr> it wraps -->
<x-page name="orders">
  <table>
    <tbody>
      <x-for each="{{rows()}}" as="row" track="id">
        <tr><td>{{row.label()}}</td></tr>
      </x-for>
    </tbody>
  </table>
</x-page>
```

```html
<!-- Works: build the grid with <div> instead -->
<x-page name="orders">
  <div class="table" style="display: grid">
    <x-for each="{{rows()}}" as="row" track="id">
      <div class="table-row">{{row.label()}}</div>
    </x-for>
  </div>
</x-page>
```

If the source HTML being migrated uses a real `<table>` and the rows aren't generated by a loop, an actual `<table>` is fine to keep as-is — the bug only bites when `<x-for>`/`<x-if>`/`<x-import>` needs to sit directly inside the table structure.

## Shadow DOM: `:host` vs `html`/`body`/`:root`

Every `<x-page>`, `<x-component>`, and `<x-component-instance>` mounts into its **own, separate Shadow DOM** — a sealed subtree the light-DOM document can't select into, and vice versa.

- A `<style>` written directly under `<x-app>` is adopted onto the **real document** — ordinary `html`/`body`/`:root` selectors there behave exactly as in a normal page, and it's also carried into every page's shadow root automatically (so it acts like a shared base stylesheet).
- A `<style>` written under `<x-page>` or `<x-component>` is scoped to **that node's own shadow root**. Inside it, `html`, `body`, and `:root` selectors match **nothing** — there is no `<html>`/`<body>` inside a shadow root. To style the page/component's own root element (background, sizing, a reset that was on `body` in the original site), select `:host` instead.

```css
/* Inside <x-app>'s <style>: real document, normal selectors */
html, body { margin: 0; font-family: system-ui; }
:root { --brand: #4f46e5; }

/* Inside one <x-page>'s <style>: shadow-scoped, use :host for the root */
:host { display: block; background: #0b0b12; color: #eee; }
```

CSS custom properties are the one thing that still cascades through the shadow boundary from the real document (`:root { --brand: ... }` at the app level is visible inside every shadow root), but box-model / reset rules like `body { margin: 0 }` do not — put those at the app level too, but know they only affect the real document's body, not each page's shadow host (use `:host { margin: 0 }` per page/component if a reset needs to apply to the shadow host itself).

When migrating a site whose CSS targets `html`/`body`/`:root`, decide per-rule: global resets/tokens → app-level `<style>` as-is; anything meant to style one specific page/component's own box → move into that node's `<style>` and rewrite the selector to `:host`.

## No imperative DOM access

Because rendered markup is sealed inside a shadow root, `document.querySelector`/`getElementById`, `.innerHTML =`, `addEventListener` calls from a script, and `<template>` cloning **only see the light DOM** — they don't error, they just silently find nothing, so the page mounts an empty shell or a dead handler. All rendering must be declarative: `<x-variable>` signals driving `{{ }}` / `x-if` / `x-for` / `class.`/`style.` bindings, never DOM surgery from `onMount()` or an event handler.

**Last resort, not a habit**: `drx.page.root` / `drx.component.root` (a script only, no template equivalent) expose the page's or component's own shadow root, for the rare case the declarative surface genuinely can't express something — third-party widget integration, focus management, measuring layout. Reach for `<x-variable>`/`{{ }}`/`x-if`/`x-for` first every time; using `root` to hand-write rendering logic fights the reconciler instead of working with it, and defeats the whole point of the declarative model. If a migration seems to need it, that's usually a sign the original imperative code wasn't re-expressed as state yet (see [Porting old imperative JS](#porting-old-imperative-js)) — check that before reaching for `root`.

## Component isolation is total

A `<x-component>` cannot see app/page variables, assets, APIs, services, or even an **enclosing** component's declarations — no matter how deeply it's nested visually. It can only resolve its own directly-declared `<x-component>` children, or the app's top-level ones. Anything it needs must be redeclared locally inside it. `<x-page-container>`, by contrast, shares its host's full app context — it isn't sandboxed at all.

Use this to decide component vs. page-container when porting reusable layout pieces: a shared header/sidebar that reads app state → `<x-page-container>`; a genuinely standalone, reusable widget (a card, a rating control, a modal body) → `<x-component>` with explicit props/events.

## Reserved names

| Where | Reserved | Why |
| --- | --- | --- |
| `<x-variable name>` at app/page scope | `asset`, `modal` | Shadows the built-in `asset`/`modal` local, breaking every expression that uses it |
| `<x-variable name>` at component scope | `asset` | Same, for the component-local `asset` built-in |
| `<x-property name>` / `<x-event name>` | `id`, `component`, `asset` | Collide with a component instance's own reserved attributes — a consumer can never set these |

Also: every variable name, component event name, and `<x-for>` alias (`as`/`index`/`key`) must be a valid JS identifier (`/^[A-Za-z_$][\w$]*$/`) — it becomes a bare identifier in expression scope. A name like `user-name` or `2fa` breaks every `{{ }}` expression that references it.

## Signal call semantics

A `<x-variable name="count">` becomes a callable `count`: `count()` reads, `count(value)` writes. Nested paths are signals too, and the preferred subscription granularity — `profile.name()` re-renders only on that path; `profile()` re-renders on any change anywhere in the object. Never write `count = value` or read a variable without calling it — both fail silently or produce `[object Object]`-style output rather than an error.

## `<x-variable>` body is strict JSON

The body is parsed with `JSON.parse`, not evaluated as JS — no trailing commas, no unquoted keys, no comments, no expressions like `Date.now()`. Booleans/null are lowercase `true`/`false`/`null` as in JSON. If a starting value needs computation, set it from `onMount()` in a script instead of the literal body.

## One script, one style, per node

Only the **first** direct-child `<script type="application/typescript">` and the **first** direct-child `<style>` under any app/page/component/service are read — extras are silently ignored, not merged and not an error. Consolidate into one of each per node.

## Event attributes are never `{{ }}`

`onclick`, `onchange`, etc. are plain calls resolved against the script's methods or a signal, evaluated fresh on each event — never wrap them in `{{ }}`. `onclick="count(count() + 1)"` is correct; `onclick="{{count(count() + 1)}}"` is not an event handler at all (it's parsed as one more `{{ }}`-interpolated attribute, evaluated once, not on click).

## Boolean/nullish attributes

An attribute bound to an expression that evaluates to `false`, `null`, or `undefined` is **removed** from the element entirely; `true` sets it as an empty-string boolean attribute (`disabled`, `checked`, `required`, `readonly`, ...). So `disabled="{{isSaving()}}"` works directly with a boolean signal — no need to stringify or use `class.`-style tricks for HTML boolean attributes.

## `class.`/`style.` need a name after the dot

`class.<name>` toggles one class by truthiness; `style.<property>` sets one inline CSS property. Both require the actual name/property after the dot — a bare `class.` or `style.` attribute is a validation error (`DRX016`), not silently ignored.

## `<x-import>` is a compile-time splice

`<x-import src>` behaves like a literal paste, resolved before the app runs — not a lazy-loaded module, not a runtime `fetch`. Treat the imported file's content as if it were typed inline at that position.

## `<x-page-container>`'s `page` is reactive — it remounts

`*page` is an expression. Every time it changes, the previously embedded page is unmounted and the new one mounted fresh — any **page-scoped** `<x-variable>` on the outgoing page is gone, not preserved. Prefer a literal `page="header"` for a slot whose page never changes, to avoid that reactive layer entirely.

This bites a common migration case directly: porting a JS-driven "page switcher" (several sections shown/hidden by toggling a class, all still in the DOM) onto a `<x-page-container>` shell changes the semantics — the original never destroyed the hidden section's state, a remounting `<x-page-container>` does. Only the app itself persists across the swap (it mounts once, before any page). So any state that must survive switching which page is shown — a counter, a form draft, scroll position — belongs in an **app-level** `<x-variable>` (declared directly under `<x-app>`), not a page-level one: a page embedded via `<x-page-container>` reads and writes app-level variables exactly like the shell does, both as bare identifiers in its template and via `drx.app.variables.<n>` in its script, because it shares the host's full app context (see [Component isolation is total](#component-isolation-is-total) above — the opposite case, for contrast). State genuinely local to one page (never referenced elsewhere) is fine to leave page-scoped; it just resets on remount, matching a fresh page load.

## Porting old imperative JS

When converting an existing static HTML+JS page, don't carry over its imperative rendering code (manual slot/template swapping, `innerHTML` diffing, hand-wired listeners) — that's exactly what trips [No imperative DOM access](#no-imperative-dom-access) above, and it looks reasonable enough to survive a fast port unnoticed. Re-express its state as `<x-variable>`s and its rendering as `{{ }}`/`x-if`/`x-for` from scratch; treat the old JS as a **spec of what the page shows and does**, not code to reuse. See [migration.md](migration.md) for the full workflow.
