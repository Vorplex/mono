# Migrating an existing HTML page/site to DRX

Follow this workflow in order. The goal is a DRX app that renders as close to pixel-identical to the source as the tools available allow, with the source's *behavior* re-expressed declaratively rather than its old imperative code reused. Read [gotchas.md](gotchas.md) in full before step 3 if you haven't already.

```
Migration progress:
- [ ] 1. Inventory the source
- [ ] 2. Decide the shape (single page, shell + pages, router)
- [ ] 3. Port structure and styling
- [ ] 4. Re-express state and behavior declaratively
- [ ] 5. Extract reusable pieces into components
- [ ] 6. Self-check against the rules
- [ ] 7. Ask for a visual check
```

## 1. Inventory the source

Read the whole source file(s) before writing anything. Note:

- Every distinct "screen" or view (even if the original toggles them with JS instead of real navigation) — each becomes an `<x-page>`.
- Shared chrome across screens (nav, header, footer, sidebar) — becomes a shared page part (see [patterns.md](patterns.md#pages-as-page-parts-composed-with-page-containers)) or lives directly in `<x-app>` if it's truly global shell (see [patterns.md](patterns.md#shell-architecture-nav--content-area)).
- Every place client-side JS mutates the DOM based on some piece of data — that data becomes an `<x-variable>`; the mutation becomes a `{{ }}`/`class.`/`style.`/`x-if`/`x-for` binding.
- `<table>` markup that's generated by a loop in JS, or that will need `<x-for>` — flag it now, it needs the `<div style="display:grid">` treatment from [gotchas.md](gotchas.md#table-layouts-the-table-orphan-bug), not a literal port.
- Any `<style>` rule targeting `html`, `body`, or `:root` — flag whether it's a true global reset/token (→ app-level `<style>`) or really meant to style one screen's own root box (→ that page's `<style>` with `:host`). See [gotchas.md](gotchas.md#shadow-dom-host-vs-htmlbodyroot).
- Fetch/XHR calls to a backend → become `<x-api>`/`<x-endpoint>` declarations.
- Modal/dialog UI → becomes an `<x-page>` opened with `.showModal()`.

## 2. Decide the shape

Use [patterns.md](patterns.md#decision-guide-page-vs-page-container-vs-component) to decide, per piece of the inventory: page, page-container, or component. Sketch the page list and shell before writing markup — changing this after the fact means re-plumbing state.

## 3. Port structure and styling

Write the actual `<x-*>` markup and CSS. Plain HTML elements, classes, and inline styles carry over directly — DRX doesn't require rewriting ordinary markup, only the app/page/component boundaries and the `:host` rule for shadow-scoped styles. Keep the original class names and CSS as close to verbatim as possible; the goal is visual fidelity, not a restyle.

## 4. Re-express state and behavior declaratively

For each place the original JS read/wrote the DOM: introduce an `<x-variable>` for the underlying data, then drive the same visual effect with `{{ }}`, `class.<name>`, `style.<property>`, `<x-if>`, or `<x-for>` instead of the original imperative code. Event listeners become `onclick`/`onchange`/etc. attributes calling a script method or a variable directly. See [gotchas.md](gotchas.md#porting-old-imperative-js) — do not carry the old DOM-manipulation code over even temporarily, it silently no-ops under Shadow DOM.

If the shell in step 2 uses a `<x-page-container>` to swap which "screen" is shown (the common shape for a site whose original JS toggled sections with a `hidden`/`active` class instead of real page loads), decide **where each piece of state lives before writing it**: anything that must survive switching screens goes in an app-level `<x-variable>`, not a page-level one — a `<x-page-container>`'s embedded page fully remounts on every switch, discarding page-scoped state. See [gotchas.md](gotchas.md#x-page-containers-page-is-reactive--it-remounts).

## 5. Extract reusable pieces into components

Once the page-level port works, look for pieces repeated across pages/lists with no dependency on their surroundings (cards, list rows, badges, form controls) and extract them into `<x-component>`s per [patterns.md](patterns.md#components-for-isolated-reused-widgets). Don't do this before step 4 — isolating too early means re-plumbing props once the real data shape is known.

## 6. Self-check against the rules

Before calling the migration done, re-read the produced markup against this checklist (mirrors DRX's own validator):

- [ ] Every `<x-page>`/`<x-component>`/`<x-variable>`/`<x-type>`/`<x-service>`/`<x-asset>`/`<x-api>` is a **direct child of `<x-app>`** (or of its owning `<x-component>`), never a sibling written after `</x-app>` closes — see [gotchas.md](gotchas.md#declarations-are-children-of-x-app-never-siblings-after-it).
- [ ] Every `<x-page>`/`<x-component>`/`<x-variable>`/`<x-type>`/`<x-service>`/`<x-asset>`/`<x-api>` name is non-empty and unique among its siblings.
- [ ] Every variable name, component prop/event name, and `<x-for>` alias (`as`/`index`/`key`) is a valid identifier (no hyphens, doesn't start with a digit) — but `<x-page name>`/`<x-component name>`/`<x-asset name>` don't need to be, they're referenced as plain strings (see [reference.md](reference.md#naming-identifiers-vs-plain-strings)).
- [ ] No variable is named `asset` or `modal`; no component prop/event is named `id`, `component`, or `asset`.
- [ ] No `<x-if>`/`<x-for>`/`<x-import>` sits directly inside `<table>`/`<tbody>`/`<tr>`.
- [ ] Every `<x-page-container page>` / `<x-component-instance component>` name matches a page/component that actually exists.
- [ ] Every `<x-route route>` pattern is valid (`/segment/{param}` shape) and no `<x-route>` sits inside a `<x-component>` (components have no router).
- [ ] Every `<x-variable>` body is valid JSON, not a JS literal.
- [ ] No `class.`/`style.` attribute is missing its name after the dot.
- [ ] Every `<x-endpoint path>` `{placeholder}` has a matching `<x-parameter>`.
- [ ] No script/style-scoped selector uses `html`/`body`/`:root` where `:host` was meant (page/component-level `<style>` only).
- [ ] No script calls `document.querySelector`/`.innerHTML =`/`addEventListener` — everything renders through signals and template bindings.

If any check fails because of what looks like a DRX defect rather than a mistake in the generated markup, stop and report it per [SKILL.md](SKILL.md#if-something-looks-like-a-drx-bug-not-a-mistake-in-the-generated-markup) instead of working around it.

## 7. Ask for a visual check

There is no headless browser available while authoring — open the produced file in a real browser side-by-side with the original (or ask the user to) to confirm the visual/behavioral match, especially anything involving Shadow DOM styling, fonts, or third-party embeds. Call out explicitly which parts you couldn't self-verify.
