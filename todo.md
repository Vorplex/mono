# SHTML — Plan

## Open problems

- [ ] `<x-if>`/`<x-for>`/`<x-import>` get foster-parented out of restricted-content-model parents (`<table>`/`<tbody>`/`<tr>`, likely `<select>`/`<colgroup>` too) because SHTML source is parsed via `DOMParser`/`text/html`, which enforces real HTML5 insertion-mode rules — see [HTML Content Model Constraints](docs/concepts/html-content-model.md) for the mechanism and the current div-based workaround. Leading candidate fix: in `ImportResolver.resolve`'s `resolver()`, rewrite `<x-if>`/`<x-for>`/`<x-import>` (open+close tags only, attributes untouched, skipping `<script>`/`<style>` regions) to `<template data-shtml-tag="...">`/`</template>` before calling `parseFromString` — `<template>` is spec-exempt from every restricted content model, so it's never foster-parented, and its content parses correctly regardless of the ambient table/select context. Requires: `Shtml.template()`'s dispatch to match `TEMPLATE` + `data-shtml-tag` instead of the literal tag name; `IfNode`/`ForNode.fromElement` to read `element.content.childNodes` instead of `element.childNodes`; `ImportResolver`'s own `x-import` scan to match the renamed marker and recurse into nested `template.content` (since an `<x-import>` can sit inside an `<x-for>`/`<x-if>` body). Always-on/unconditional rename (harmless outside restricted parents too) — no author-facing syntax change. Not yet implemented.
